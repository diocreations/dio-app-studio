# The editor architecture

This is the working record of how the visual editor is built, what it shares with
the published app, and what is deliberately still ahead. It exists so the next
change starts from the same model rather than inventing a parallel one.

## Audit

The build was already a deterministic renderer, not a page builder:

- `buildSpec()` (`src/worker/pricing.ts` + verticals/importers) produces one
  `AppSpec`, stored as JSON on the project row. It carries the business, its
  catalogue, features, chosen layout, imported design kit and structure.
- `renderApp(spec, options)` selects a theme from the trade, derives a seeded
  composition (deck slot, hero, order, density, corners, media), and emits a
  complete document: HTML, generated CSS, and a small client script for the
  app's screens.
- `themeFor()` and `verticals.ts` already give the 27 trades distinct layouts,
  palettes, type pairings and navigation shells; `designsFor()` already offers
  three directions per trade on the brief.
- Persistence is one `projects` row; `saveVersion()` rebuilds and bumps the
  version, `notes` and `activity` carry review history. Exports render from the
  same `AppSpec`.

There was no component tree. Sections were composed inside layout functions and
ordered by a seeded value, so nothing could address "the offers section" as an
editable object. That was the gap.

## The shared representation

`src/worker/doc.ts` defines a small, strict document:

```ts
Doc { v, accent?, sections: DocNode[] }
DocNode { id, kind, title?, text?, cta?, style, responsive, hidden }
```

- **One document, every surface.** Generation suggests a starting `Doc`
  (`docFromSpec`), the editor reads and saves that same JSON, `/p/:token/app`
  passes it into `renderApp`, and the exported PWA bundle renders with it too.
  There is no editor-only model.
- **Stable ids.** Default sections are `sec_<kind>`; added or duplicated
  sections get a suffix. Selection, drag targets and undo snapshots refer to ids,
  not array positions.
- **Content, style and responsive kept apart.** Wording lives in `title`/`text`
  and `cta`; visual choices in `style` (background, ink, alignment, vertical
  padding, radius); device visibility in `responsive.hideOn`. Accent is one
  document-level value so every themed surface follows it.
- **Normalise on the way in.** `normalizeDoc` accepts browser input, drops
  unknown kinds, de-duplicates ids, clamps text, sanitises colours, guarantees a
  hero, and refuses to hide the hero. The renderer normalises again, so a
  document can never reach HTML unchecked.
- **Legacy builds are untouched.** A project with no saved document renders
  through the original seeded path. Opening its editor synthesises
  `docFromSpec` and the first save opts it into the document model.

### Flagships are documents, not a parallel renderer

The ten flagship trades use the same document model as every other build. A
flagship home is generated by `flagshipDocFromSpec()` in `src/worker/doc.ts` as
ordinary `DocNode`s, not as a second component tree:

```ts
{ id: 'sec_fx_dine_title', kind: 'flagship', variant: 'dine-title', title, text, media? }
```

- `kind: 'flagship'` plus a validated `variant` selects the trade-specific
  markup inside `src/worker/flagship.ts`.
- Every visible flagship block has a stable `sec_fx_*` id for the life of the
  document. Selection, drag targets, duplication and version snapshots use that
  id, never an array index.
- The trade keeps its own composition. The document controls order, copy,
  visibility, media and responsive state; it does not force a shared layout.
- `flagship` only activates when the home screen actually contains flagship
  nodes. Older generic documents keep rendering and editing exactly as before.

## Rendering

`renderApp` accepts `doc`, renders each document block through its kind (or its
flagship variant), wraps it in `<div class="doc-section" data-sec="…">` with its
responsive classes and inline style, and takes order from the document. The
editor canvas and the published `/p/:token/app` call the same renderer with the
same saved document; `editor=1` adds only the selection/drag bridge. Generic
homes keep the original hero treatment, wrapped so it stays selectable. Added
kinds (`testimonials`, `cta`) have their own markup.

A flagship CTA is part of the document order, not a fixed overlay covering the
content behind it. Restaurant, salon and professional actions sit inline after
their services or lead content; the bottom navigation remains the persistent
route to booking and enquiry.

## The editor

`/p/:token/edit` is the editor page. It and the review page redirect anonymous
visitors to owner login; the noindex header and meta stay on both:

- **Left** — add-section tiles (only kinds the build can render, disabled when
  present) and a draggable structure list with show/hide, duplicate, delete.
- **Centre** — a live, server-rendered iframe at desktop/tablet/mobile widths.
  Tapping any flagship block selects it, outlines it in the canvas and opens the
  contextual quick-edit dock. The dock edits heading and words immediately and
  exposes photo, move up/down, duplicate, hide, delete and More. The same block
  can be dragged to reorder against its neighbour.
- **Right** — heading, words, alignment, background, spacing, corners and
  per-device visibility for the selected section, plus delete. For flagship
  blocks with a photograph it also exposes replace/library, focal-point drag,
  fit and crop shape.
- **Toolbar** — undo/redo (buttons and ⌘Z / ⇧⌘Z, 60 snapshots), save status,
  device switcher, review link and the live app.
- **Autosave** — debounced PUT of the whole document; the preview reloads from
  the stored document so the canvas is never a client-only illusion.
- **AI preview** — `/api/projects/:token/doc/ai` proposes a changed document and
  a summary; nothing is stored until "Apply". Apply pushes history, so it is
  undoable like any manual edit.

`applyCommand` is an honest local vocabulary (premium/modern/warm/minimal/bold,
add testimonials or CTA, improve the hero, rearrange, clear device hiding, set a
colour). It costs nothing and cannot invent customer content. A hosted model can
replace it behind the same signature.

## Security and cost

- Document reads/writes require the owner session, not the customer app token;
  every `/api/projects/:token/*` route sits behind that session middleware,
  cross-origin JSON writes are refused and bodies are capped at 256 KB.
- Every document is normalised server-side; section ids are regex-bound and
  colour values sanitised, and all text is escaped by the renderer.
- Autosave writes one row and one activity entry; there is no extra request
  metering, no external call, and the app page remains the only read path.
- `/p/*` stays noindex in HTML and headers; `/p/:token/edit` inherits both.

## Media and catalogue

Image components carry a `MediaRef` rather than a URL: media id, alt text,
intrinsic dimensions, focal point, fit and crop aspect. The inspector offers
replace, upload, library, reposition (drag the focal dot), fill/fit and aspect,
and every change goes through the document autosave and the live canvas.

Uploads are converted in the browser to 320/640/1280 WebP variants, then
validated server-side and stored in R2 by content hash. The Photos button opens
the owner's library with dimensions, format, reuse and deletion; deletion is
refused while the current document uses an image, and old versions are scrubbed
so cleanup is still possible. Trade-aware photo briefs suggest what to
photograph, but never invent business photographs.

The Catalogue button edits the customer-facing catalogue and offers: category
names, item names, short descriptions, prices and offers. It writes the app spec
only, so saving content does not create a new document or lose the owner's
layout work. Each item also has a photo control: the chosen media library image
is stored on the item with its own alt text, focal point and fit, and overrides
the trade's stock scene in every renderer. The library exposes search, All / In
use / Not used filters, dimensions and delivered byte sizes; replacement keeps
the media id so item and document references survive. Deleting an image still in
use is refused.

## What is verified

Browser acceptance on all five flagship builds covered: direct selection,
text edit, image upload/replacement, focal-point drag, drag reorder, autosave and
reload, published app reflecting the saved document, undo/redo, and restoring an
earlier version. The app and editor were measured at 320, 375, 390 and 430px
with no horizontal page overflow. See `docs/DESIGN_QA.md` for the exact flows,
URLs and captures.

Batch 3 repeated the document checks on the trades app through the real editor
UI (`scripts/verify-batch3-editor.mjs`): tapping a section in the phone preview
selected it; a heading edit autosaved and appeared in the stored document; undo
restored it; a component added from the library, then removed by undo; a
dragged component moved above its neighbour and undo restored the order; hide
persisted, disappeared from the published app, and undo brought it back;
duplicate and delete changed the count and returned it; and version history
listed saved versions and restored one. The script restores the demo document
at the end. The same autosave endpoint and version table serve all fifteen
flagship trades.

### Direct controls added in the visual pass

The quick dock now edits more than heading and body copy:

- **Buttons:** any flagship action exposes its label and destination screen. The
  destination list is built from the document's current screens.
- **Background and text:** five background choices (automatic, paper, sand, ink
  and the project accent) plus automatic/ink/white text. These write the same
  `style` fields the full inspector uses, so there is no second document model.
- **Cards and prices:** catalogue-backed blocks show an **Items & prices**
  shortcut that opens the existing catalogue editor; product names,
  descriptions, prices and offers remain in one owner-authored place.
- **Photos:** the photo action opens the owner's media library; uploads are
  converted to responsive WebP and stored in R2, and uploaded media overrides the
  local stock scene on the selected block.
- **Screen navigation:** screen name and “show in bottom navigation” remain in
  the right inspector, while the rebuild/duplicate/delete controls stay on the
  screen list.

A sample-content strip appears above the canvas when a build still uses trade
defaults for menu, contact, story, offers or team content. “Items & prices” opens
the catalogue editor; “Details” goes to the dashboard. Content imported from the
owner's site is not labelled sample. The dashboard's Application settings panel
can update the name, brand colour, tagline, contact, story and team, and remove
only the groups still marked as examples after confirmation. Saving a changed
catalogue claims it as the owner's; an untouched save leaves it flagged.

The new controls were exercised at 390px: action label, destination and
background all persisted through autosave and a published-app reload; the retail
products block showed the catalogue shortcut; and a QA WebP was uploaded, applied
through the library and served by the published app before being removed. Width
checks at 320, 375, 390 and 430px found no editor page overflow.

## What this slice is not

Still ahead, in rough order of value:

1. Element-level nodes inside a flagship block (separate text, button and image
   targets) and inline canvas text editing. The current flagships expose whole
   composition blocks, which is the right granularity for their layouts.
2. A hosted AI model behind `applyCommand` with per-user limits; photo briefs
   are currently deterministic trade-aware suggestions, not generated images.
3. Per-breakpoint style overrides beyond show/hide, and saved design presets.
4. Migrating the remaining 17 trades to their own flagship compositions, after
   this unified architecture has been signed off.

The editor is intentionally composition-first: a restaurant owner can reorder,
rewrite, photograph and hide whole flagship blocks without meeting a property
grid they cannot interpret. Element-level control is the next layer, not a
replacement.
